# 11-observability — design

## Зачем

Сага из 10 работает, но изнутри её не видно: где застрял заказ, какой шаг ждал, почему пошла компенсация —
это сейчас читается только из истории в API и логов четырёх контейнеров. Здесь сага становится **наблюдаемой**:
один заказ = **один трейс** через HTTP, Kafka и outbox во всех четырёх сервисах; метрики саги на дашборде;
JSON-логи с trace id, переход «спан → логи» в один клик.

Главное (выбор Dmitry): **трейсы в первую очередь** — открыл заказ, увидел всю сагу одним трейсом. Метрики —
чтобы заметить проблему, логи — чтобы из спана дойти до подробностей.

Успех: по `docs/start.md` любой сценарий 10 повторяется руками и разбирается в Grafana; e2e проверяет трейсы
через API Tempo; learning notes содержат сравнение «Boot-инструментирование vs Java-агент» и «outbox с
переносом контекста vs без».

## Цели / не-цели / анти-цели

- Цели: распределённый трейсинг (W3C `traceparent`) через HTTP, Kafka и **outbox, включая переотправку**;
  сравнение двух способов инструментирования в одном трейсе; метрики саги и outbox; структурные JSON-логи с
  trace id в Loki; один дашборд и одно правило алерта; корреляция трейс ↔ логи ↔ метрики в Grafana.
- Не-цели: k8s (Prometheus/Loki/Tempo в кластере — в 12), профилирование (Pyroscope — в learning notes),
  продакшен-хранилища и retention, sampling-стратегии сложнее «100 %» (в learning notes: tail sampling).
- Анти-цели: трейс саги, который «развалился» на куски так, что их нельзя собрать; телеметрия, которая ломает
  бизнес-поведение (без Grafana/коллектора сервисы обязаны работать как в 10); дашборд из стандартных панелей
  JVM без единой метрики предметной области.

## Подход

| Вариант | Решение |
|---|---|
| (A) Boot-инструментирование на трёх сервисах + Java-агент на одном, Compose, `grafana/otel-lgtm` | ✔ |
| (B) только агент везде, отдельные контейнеры Prometheus/Loki/Tempo/Grafana/Collector | нет — нечего сравнивать, outbox не решается осознанно |
| (C) как A, но в kind (kube-prometheus-stack, Loki, Tempo через Argo CD) | нет — тяжело; кластерный Prometheus естественнее в 12 (HPA, KEDA) |

## Состав (Compose, без k8s)

Копия четырёх сервисов 10 (`ordering`, `payment`, `inventory`, `delivery`) с тем же поведением, API, топиками,
рычагами и бизнес-правилами (их спецификация — `10-outbox-saga/docs/superpowers/specs/2026-11-18-10-outbox-saga-design.md`,
здесь не повторяется). Пакеты `de.ibikus.appa.hephaestus.observability.<service>`; образы
`hephaestus/observability-<service>`. Kafka 4.2.2, PostgreSQL 17 с четырьмя базами, Kafka UI, плюс
**`grafana/otel-lgtm`** (один контейнер: OTel Collector, Prometheus, Loki, Tempo, Grafana; версия закреплена,
не `latest`). Порты сервисов 8080–8083 как в 10; Grafana `127.0.0.1:3000`; OTLP 4317/4318 — только внутри
сети Compose (и на 127.0.0.1 для запуска сервиса из IDE).

## Инструментирование: два способа рядом

- **Ordering, Payment, Inventory — средствами Boot 4**: `spring-boot-starter-opentelemetry` (Micrometer
  Observation + Micrometer Tracing с мостом в OpenTelemetry, OTLP-экспорт трейсов, метрик и логов); логи в OTLP
  через OpenTelemetry Logback appender. Наблюдения включены для Spring MVC, `RestClient` (если есть), JDBC
  (если без лишней зависимости не выходит — learning notes), **Kafka** (`observation-enabled` у
  `KafkaTemplate` и listener-контейнеров), `@Scheduled`.
- **Delivery — только OpenTelemetry Java-агент**, без телеметрических зависимостей в коде. Агент (версия
  закреплена) кладётся в образ Jib и подключается `-javaagent`; конфиг — переменные `OTEL_*`. В тестах
  Delivery агента нет — IT проверяют поведение, как в 10.
- **Delivery остаётся «чистым агентом» и в outbox** (решение Dmitry): контекст в своих исходящих сообщениях
  Delivery сам не сохраняет. Первая (асинхронная) отправка остаётся в трейсе — агент переносит контекст через
  пулы потоков; **переотправка** публикации Delivery планировщиком начинает новый трейс. Это намеренно видимый
  минус подхода «без кода» (learning notes), а не ошибка. Поле/заголовок с контекстом в сообщении Delivery
  принимает и игнорирует.
- Оба шлют по OTLP в `otel-lgtm`; `service.name` = имя сервиса; sampling 100 %.
- Сравнение (learning notes + сценарий в `start.md`): имена и атрибуты спанов (Micrometer-конвенции vs OTel
  semantic conventions), что видно в JDBC/Kafka/MVC, какие метрики появляются, стоимость (размер образа,
  время старта), как настраивается.

## Трейс через outbox — главный опыт

Событие уходит в Kafka не в рамках запроса: Spring Modulith публикует его после коммита (асинхронно), а
незавершённые публикации переотправляет планировщик (`resubmitIncompletePublicationsOlderThan`) — в другом
потоке и, после сбоя Kafka, через минуты. Таблица `event_publication` контекст трейса не хранит.

- **Решение** (Ordering, Payment, Inventory): контекст (`traceparent`, W3C) захватывается в момент `Outbox.publish` (внутри транзакции
  бизнес-операции) и хранится **в самом сообщении** (поле в `OutgoingMessage`/`SagaMessage` или заголовок,
  если Modulith-экстернализация позволяет задать заголовки из события — выбор за строителем). При отправке —
  первой или повторной — продюсерский спан становится дочерним **сохранённого** контекста, а не текущего
  потока. Потребитель продолжает трейс из заголовка Kafka как обычно.
- **Рубильник** `observability.outbox.carry-trace` (env `OUTBOX_CARRY_TRACE`, по умолчанию `true`). При
  `false` поведение как «из коробки»: первая отправка, возможно, попадает в трейс (если контекст дошёл до
  асинхронного потока), переотправленная — начинает новый трейс. Рубильник нужен, чтобы увидеть разрыв руками.
- То же для **таймаута шага** оркестратора (`@Scheduled`): компенсации по таймауту продолжают трейс саги
  (контекст сохранён в строке `saga` при отправке команды) — иначе таймаут виден отдельным трейсом.
- Ключевые бизнес-атрибуты на спанах: `order.id`, `saga.style`, `saga.step`, `message.type` — по `order.id`
  трейс ищется в Tempo (TraceQL `{ span.order.id = "<id>" }`). Для Delivery (агент) атрибуты добавляются
  только тем, что агент умеет без кода; если `order.id` там не появляется — это наблюдение для сравнения, не
  ошибка.

## Метрики

Через Micrometer → OTLP → Prometheus (в `otel-lgtm`). Предметные метрики (Ordering):
- `saga.completed` (counter; теги `style`, `outcome` = confirmed|rejected, `reason`);
- `saga.duration` (timer/histogram от размещения до финального статуса; тег `style`);
- `saga.step.duration` (timer; `style`, `step`);
- `saga.timeouts` (counter; `step`).

У всех четырёх (у Delivery — если агент не даёт, то не нужно; сравнение):
- `outbox.publications.incomplete` (gauge: строки `event_publication` без `completion_date`).

Плюс стандартные метрики Boot (HTTP, JVM, Kafka-клиент) — как есть.

## Логи

JSON в stdout (`logging.structured.format.console`, формат — выбор строителя, ECS или logstash) с `traceId` и
`spanId`; те же записи — в Loki по OTLP (Boot-сервисы через Logback appender, Delivery — агент). Бизнес-события
саги (шаг, компенсация, таймаут, отказ участника) логируются на INFO с `order.id`.

## Grafana

Провижининг из файлов репозитория (монтируются в `otel-lgtm`):
- **Дашборд «Saga»**: заказы в минуту по стилю и исходу; p50/p95 `saga.duration` по стилю; длительность шагов;
  компенсации и таймауты; `outbox.publications.incomplete` по сервисам; HTTP 5xx; таблица последних трейсов
  (Tempo) с переходом.
- **Правило алерта**: `outbox.publications.incomplete > 0` дольше 1 минуты в любом сервисе (видно в сценарии
  «Kafka остановлена»). Только в Grafana, без доставки уведомлений.
- Корреляции: Tempo → Loki (логи спана по trace id), Loki → Tempo (derived field), метрики → трейсы через
  exemplars, если Micrometer/OTLP их передают (иначе — learning notes).

## Сценарии (руками в `start.md`, автоматом в e2e)

1. Успешный заказ (оба стиля): один трейс, спаны всех четырёх сервисов, включая Delivery от агента.
2. Отказ Payment/Inventory (оба стиля): в трейсе виден отказ и компенсации; метрика `outcome=rejected`.
3. Kafka остановлена → заказ → Kafka запущена: при `carry-trace=true` — **один** трейс, в нём пауза (Kafka
   остановлена до размещения, ждёт outbox Ordering; Delivery отправляет уже при живой Kafka). Алерт outbox
   срабатывает и гаснет — **только руками** (нужно держать Kafka ≥ 2 мин), в e2e не проверяется. При `carry-trace=false` (руками в `start.md`) — переотправленное событие в
   отдельном трейсе.
3a. Руками: Kafka остановить, когда заказ дошёл до Delivery — ответ Delivery переотправляется и уходит в
   отдельный трейс (минус агента).
4. Delivery остановлена, оркестрация: таймаут шага и компенсации внутри трейса саги; `saga.timeouts` растёт.
5. Медленный участник (`delayMs`): длинный спан виден в трейсе и на p95.

## Тесты

- Юнит/IT из 10 переносятся и остаются зелёными (поведение не меняется).
- IT Ordering с Testcontainers `otel-lgtm` (или in-memory exporter, если надёжнее — выбор строителя) проверяет:
  `traceparent` есть в исходящем Kafka-сообщении; **переотправленная** публикация несёт тот же trace id, что и
  исходная операция (при `carry-trace=true`) и другой (при `false`); метрика `saga.completed` растёт.
- IT: сервис стартует и работает, когда OTLP-приёмник недоступен.
- e2e (`scripts/e2e.sh`): поднимает стек, гонит сценарии 1–4 и через HTTP API Tempo проверяет состав трейсов
  (сервисы в трейсе, один trace id на заказ в сценарии 3, таймаут внутри трейса в сценарии 4; алерт и
  сценарий 3a — не проверяются); проверяет, что
  Prometheus отдаёт `saga_completed` и что Loki находит логи по trace id.
