# Learning notes — 09-events-kafka

## Партиции, ключ, порядок

Топик — набор упорядоченных журналов (партиций). Producer выбирает партицию по хешу ключа: события с одним ключом
(`customerId`) всегда в одной партиции и читаются в порядке записи. **Порядок есть только внутри партиции.**
Сменить число партиций у живого топика — сломать соответствие «ключ → партиция» для старых и новых событий.

## Consumer group

Каждая партиция в группе принадлежит ровно одному участнику. Участников больше, чем партиций, — лишние
простаивают (сценарий 6). Вход и выход участника — **ребалансировка**: партиции переезжают, на время пауза.
Разные группы читают топик независимо — у каждой свои офсеты (Notification и любая будущая аналитика).

## Доставка: at-least-once + идемпотентность

Офсет коммитится после обработки: при падении между обработкой и коммитом запись придёт ещё раз. Плюс
Ordering может отправить событие повторно (`/admin/republish`). Значит, consumer обязан быть **идемпотентным**:
таблица `processed_event` с ключом `event_id`, вставка в той же транзакции, что и результат. «Exactly once» в
Kafka (транзакции) работает только внутри Kafka (read-process-write), а не для записи в чужую БД.

## Ретраи, DLT, poison message

- Временная ошибка → повтор на месте с backoff (`DefaultErrorHandler`): пока повторяем, **партиция стоит**.
- Постоянная ошибка → после N попыток запись уходит в **DLT** с заголовками причины, партиция едет дальше.
- **Poison message** (не JSON, нет полей) — без ретраев, сразу в DLT: повтор не поможет, только задержит.
- DLT — не мусорка: нужен процесс разбора и **переотправки** после починки (`/admin/dlt/replay`).
- Альтернатива блокирующим ретраям — **неблокирующие** (`@RetryableTopic`: топики `-retry-1s`, `-retry-2s`):
  партиция не стоит, но порядок для ключа теряется.

## Dual write

«Сохранить в БД и отправить в Kafka» — две системы без общей транзакции: между шагами можно упасть. Варианты:
**transactional outbox** (тема 10), CDC (Debezium), listen-to-yourself. Синхронная отправка с `acks=all`
делает сбой видимым (503), но не атомарным.

## Producer

`acks=all` — запись подтверждена всеми in-sync репликами; `enable.idempotence=true` — ретраи producer'а не
создают дублей и не меняют порядок в партиции. `max.block.ms`, `delivery.timeout.ms` — чтобы при недоступной
Kafka запрос падал за секунды, а не висел минуту.

## Share groups (Kafka 4.2) против consumer groups

| | Consumer group | Share group |
|---|---|---|
| Единица распределения | партиция целиком | отдельная запись |
| Участников больше партиций | простаивают | все получают работу |
| Порядок по ключу | да (внутри партиции) | **нет** |
| Подтверждение | офсет (всё до него) | каждая запись (accept / release / reject) |
| Неудачная запись | ретраи блокируют партицию, затем DLT | повторная доставка любому участнику до лимита, затем архив; DLT нет |
| Подходит для | потоков с порядком, событийных моделей | очередей задач (как RabbitMQ / SQS) |

## Вопросы для собеседования

1. **Как Kafka гарантирует порядок?** Только в партиции; ключ → партиция.
2. **Сколько consumer'ов имеет смысл в группе?** Не больше числа партиций (для consumer group).
3. **At-most-once, at-least-once, exactly-once — что выбрать?** At-least-once + идемпотентный consumer.
4. **Что такое ребалансировка и чем она мешает?** Пауза, повторная доставка незакоммиченного; cooperative rebalancing.
5. **Ретраи блокирующие или неблокирующие?** Порядок против пропускной способности.
6. **Что делать с DLT?** Мониторинг, разбор, переотправка; poison message — без ретраев.
7. **Dual write: в чём проблема и решения?** Outbox, CDC.
8. **`acks=all` и idempotent producer — зачем?** Надёжность и отсутствие дублей при ретраях producer'а.
9. **Share groups против consumer groups?** Очередь задач против упорядоченного потока.
10. **JSON без Schema Registry — риски?** Совместимость контракта: добавлять поля можно, менять/удалять — нет.
