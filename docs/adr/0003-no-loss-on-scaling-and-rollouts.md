# ADR-0003: Ничего не теряем при масштабировании и обновлении — at-least-once, идемпотентность, мягкая остановка

## Контекст и проблема

Автомасштабирование и rolling update постоянно добавляют и убирают поды. Для консьюмеров Kafka это
**ребалансировка**: партиции переезжают к другим подам. Если под убит посреди обработки, сообщение либо будет
обработано повторно (смещение не закоммичено), либо — при неправильной настройке — пропущено. Для HTTP: запрос,
пришедший в под, который уже останавливается, получит ошибку. Нужно, чтобы ни одно из этого не нарушило ADR-0001.

## Движущие факторы

- ADR-0001: ноль потерянных заказов и ноль двойных эффектов.
- То, что уже есть из 10: outbox (сообщение уходит вместе с коммитом), идемпотентные участники
  (`processed_message`), подтверждение смещения после обработки записи (`ack-mode: record`).
- Kafka 4.x: новый протокол консьюмер-групп (KIP-848) — инкрементальное переназначение на стороне брокера.

## Рассмотренные варианты

- A. Классический протокол группы (eager) — как сейчас
- B. Классический протокол + `CooperativeStickyAssignor`
- C. **Новый протокол `group.protocol=consumer` (KIP-848)**
- D. Статическое членство (`group.instance.id`) — дополнительно к любому из A–C

## Решение

Выбран **C** плюс набор обязательных мер:

- **At-least-once + идемпотентность** (как в 10, не меняется): смещение коммитится после обработки;
  повтор после ребалансировки отсекается `processed_message`. Это и есть гарантия «ни потерь, ни двойных эффектов».
- **`group.protocol=consumer`**: при входе и выходе пода переезжают только затронутые партиции, остальные
  консьюмеры не останавливаются (в отличие от eager, где останавливается вся группа).
- **Мягкая остановка**: `server.shutdown=graceful` (уже есть), `spring.lifecycle.timeout-per-shutdown-phase` 20 s,
  `terminationGracePeriodSeconds` 40 s, `preStop` пауза 5 s (чтобы под успел исчезнуть из Endpoints до остановки
  приёма HTTP). Контейнер Kafka-слушателя останавливается, дорабатывая текущую запись и коммитя смещение.
- **Rolling update**: `maxUnavailable: 0`, `maxSurge: 1`; readiness-проба не пускает трафик до готовности.
- **PodDisruptionBudget** `maxUnavailable: 1` на каждый сервис: drain выселяет поды по одному и не зависает на
  сервисе с одной репликой (с `minAvailable: 1` и одной репликой drain ждал бы вечно). У Ordering минимум 2
  реплики (ADR-0002), поэтому вход HTTP при drain не пропадает; участники с одной репликой ненадолго
  останавливаются — сообщения ждут в Kafka.
- Статическое членство (D) **не** используем: при масштабировании вниз партиции ушедшего пода висят без
  консьюмера до истечения `session.timeout.ms` — для автомасштабирования это хуже.

### Последствия

- Хорошо: гарантия держится на двух независимых механизмах (outbox + идемпотентность), настройки остановки лишь
  уменьшают число повторов и пауз.
- Плохо: повторы при ребалансировке всё равно возможны — они видны в `/admin/stats` (duplicates) и это нормально.
- Плохо: `group.protocol=consumer` — относительно новый; нужна совместимость клиента (Kafka-клиенты 4.x) и брокера
  Strimzi (Kafka 4.x).

### Подтверждение

Сценарии ADR-0005 (rolling restart, удаление подов, drain узла) во время пика + сверка ADR-0001.

## Плюсы и минусы вариантов

### A. Eager

- Хорошо: просто, знакомо.
- Плохо: каждый вход/выход пода останавливает всю группу — при автомасштабировании «шторм ребалансировок».

### B. CooperativeStickyAssignor

- Хорошо: инкрементально, работает на любых брокерах.
- Плохо: логика на клиенте, несколько раундов; в Kafka 4 есть решение лучше.

### D. Статическое членство

- Хорошо: быстрый перезапуск того же пода без ребалансировки (rolling update).
- Плохо: при масштабировании вниз — простой партиций до таймаута сессии.
