# ADR-0001: Критерий успеха «пиковой распродажи» — ни один принятый заказ не потерян

## Контекст и проблема

12 гоняет сагу заказа (сервисы из 11) под пиковой нагрузкой в кластере, с автомасштабированием, перезапусками и
отказами подов. Нужно заранее, до прогона, решить, что значит «система выдержала»: иначе зелёный отчёт нагрузочного
теста ничего не доказывает. Типичная ловушка — смотреть только на задержку HTTP: быстрый ответ с ошибкой выглядит
здоровым на графике задержек.

## Движущие факторы

- Главное (решение Dmitry): **заказ не должен потеряться.**
- Критерии формулируются до прогона и проверяются машиной (exit code), а не глазами.
- Помимо деловой корректности — обычные SLO: задержка в хвосте и доля ошибок, и восстановление без ручного вмешательства.

## Рассмотренные варианты

- A. Только SLO по HTTP (p95/p99, доля 5xx) — как в большинстве гайдов по нагрузочному тесту
- B. Деловой инвариант «ноль потерянных заказов» + SLO по HTTP + восстановление очереди
- C. Только деловой инвариант

## Решение

Выбран **B**. Прогон успешен, если выполнены **все** условия:

1. **Ноль потерянных заказов** (главное). Каждый заказ, на который Ordering ответил `202 Accepted`, через
   ограниченное время после конца нагрузки (≤ 5 мин) имеет финальный статус `CONFIRMED` или `REJECTED` — ни одного
   `PENDING`, ни одного отсутствующего. Сверка: id из ответов Gatling ↔ строки `purchase_order` в базе Ordering.
2. **Нет двойных эффектов**: у каждого подтверждённого заказа ровно один резерв денег и товара (суммы резервов в
   Payment и Inventory сходятся с подтверждёнными заказами).
3. **SLO HTTP** на приём заказа (`POST /api/orders`) за весь прогон: p95 < 500 ms, p99 < 2 s, доля ответов не-2xx
   < 0.1 %. Ответы «перегружен» (`429`/`503`), если появятся, считаются ошибками.
4. **Восстановление**: лаг консьюмер-групп возвращается к нулю ≤ 3 мин после конца пика, реплики сходятся к
   минимуму ≤ 10 мин, без ручных действий.

Числа в 3–4 — стартовые (типичные значения для e-commerce из открытых гайдов), уточняются после первого
прогона по реальной ёмкости kind на ноутбуке и фиксируются в этом ADR.

### Последствия

- Хорошо: проверка ловит то, что HTTP-метрики не видят — заказ, принятый и брошенный посреди саги.
- Хорошо: тот же инвариант проверяет и масштабирование, и rolling update, и отказы подов (ADR-0003, ADR-0005).
- Плохо: нужна сверка после прогона (скрипт с доступом к базе), а не только отчёт Gatling.

### Подтверждение

Gatling-assertions (п. 3) валят сборку; скрипт сверки (п. 1–2, 4) возвращает ненулевой код. Оба — в
`12-scaling-operations/scripts/peak.sh`.

## Плюсы и минусы вариантов

### A. Только SLO по HTTP

- Хорошо: стандартно, Gatling умеет из коробки.
- Плохо: асинхронная сага может «потерять» заказ после 202 — HTTP этого не увидит.

### C. Только деловой инвариант

- Хорошо: прямо отвечает на «заказ не потерян».
- Плохо: система, отвечающая по 10 s, формально проходит.
