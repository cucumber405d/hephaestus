# ADR-0000: Решения записываем как ADR в формате MADR, в Markdown

## Контекст и проблема

До 12 решения жили внутри спецификаций подпроектов (таблицы «Подход») и в impact-файлах. Чтобы найти, *почему*
выбрано то или иное, приходится читать спеку целиком; решения, общие для нескольких подпроектов, размазаны. Нужен
один формат и одно место для архитектурных решений.

## Движущие факторы

- Documentation as Code: всё в репозитории, в Markdown, рядом с кодом (правило проекта).
- Решение должно читаться отдельно от спеки: контекст, варианты, выбор, последствия.
- Портфолио: формат, знакомый ревьюерам на рынке.
- Лёгкость: без инструментов, просто файлы.

## Рассмотренные варианты

- MADR 4.0 (Markdown Architectural Decision Records)
- Шаблон Майкла Найгарда (2011)
- Y-statements (Zimmermann)
- Без формата — решения только в спеках

## Решение

Выбран **MADR 4.0**, потому что он сохраняет рассмотренные варианты с плюсами и минусами (именно это мы и так
делаем в спеках), остаётся лёгким и широко распространён.

Правила хранения:

- Каталог `docs/adr/` в корне репозитория; сквозная нумерация `NNNN-kebab-title.md` для всех подпроектов.
- Каждый ADR — YAML front matter (`status`, `date`, `decision-makers`, `scope`), разделы по `template.md`.
- Язык — русский (как вся документация в `docs/`); названия технологий и цитаты — как есть.
- Статусы: `proposed` → `accepted` | `rejected`; позже `deprecated` или `superseded by ADR-NNNN`.
  Принятый ADR не переписывается по существу: изменение решения — новый ADR, старый получает `superseded`.
- `README.md` — реестр: номер, название, статус, область. Обновляется в том же коммите, что и ADR.
- Спецификация подпроекта ссылается на свои ADR, а не повторяет их.
- Решения подпроектов 01–11 остаются в их спеках; переносятся в ADR только при пересмотре.

### Последствия

- Хорошо: «почему» ищется по реестру; общие решения (платформа, наблюдаемость) — в одном месте.
- Плохо: ещё один документ на каждое решение; реестр надо держать в актуальном состоянии вручную.
