# ADR-0005: Помехи во время пика — обновление, удаление подов, drain узла

## Контекст и проблема

Автомасштабирование само по себе меняет состав подов, но самые опасные моменты — плановые и внеплановые
остановки во время пика: выкатка новой версии, падение пода, обслуживание узла. ADR-0001 должен держаться и тогда.

## Движущие факторы

- «Заказ не должен потеряться» — в том числе при перезапусках.
- Сценарии должны быть воспроизводимы скриптом.

## Рассмотренные варианты

- A. Только нагрузка, без помех
- B. **Нагрузка + набор помех по сценарию** (скрипт)
- C. Chaos-инструмент (Chaos Mesh, Litmus)

## Решение

Выбран **B**. `peak.sh` принимает сценарий:

1. `scale` — только нагрузка, смотрим автомасштабирование.
2. `rollout` — посреди пика `kubectl rollout restart` всех четырёх деплойментов (как выкатка версии).
3. `kill` — посреди пика удаляет по одному поду каждого участника (`kubectl delete pod`, мягко) и один —
   жёстко (`--grace-period=0 --force`, как падение).
4. `drain` — `kubectl drain` того worker-узла, на котором **нет** Kafka, PostgreSQL (CNPG) и lgtm (скрипт
   выбирает узел по расположению их подов), потом `uncordon`. Брокер Kafka один и на эфемерном хранилище: его
   выселение потеряло бы сообщения не по вине сервисов — это проверка платформы, а не 12 (learning notes:
   реплики брокера, rack awareness). PDB — по ADR-0003.

Каждый сценарий завершается сверкой ADR-0001.

### Последствия

- Хорошо: проверяем ровно то, что обещает ADR-0003, без новых инструментов.
- Плохо: жёсткое убийство пода гарантированно даёт повторы — они ожидаемы и должны отсекаться идемпотентностью.

### Подтверждение

Все четыре сценария проходят сверку; e2e в CI — `scale` и `rollout` (в CI-раннере ресурсы скромнее).
