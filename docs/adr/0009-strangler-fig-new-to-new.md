# ADR-0009: Strangler Fig для Forge — «новые в новый, старые доживают в старом»

## Контекст и проблема

Forge выносится из модульного монолита в отдельный сервис без остановки приёма заказов. Пока идёт перенос, заказы
на ковку существуют в двух системах. Главный вопрос любого «удушения» — что делать с данными: перенести,
синхронизировать или разделить.

## Движущие факторы

- Ни одной остановки приёма заказов, никакого «большого взрыва».
- Ни один заказ на ковку не теряется и не выполняется дважды (проверяет сверка).
- Нет общей базы монолита и сервиса после переключения (иначе — распределённый монолит).
- Возможен откат.

## Рассмотренные варианты

- **A. Новые в новый, старые доживают в старом.** Новые заказы идут в сервис, начатые в монолите там и
  заканчиваются. Синхронизации нет.
- **B. Одномоментный переезд.** Миграционный Job копирует таблицы, потом переключение 100 % трафика.
- **C. Двойная запись и сверка** (parallel run): обе системы ведут те же заказы, пока новой не начнут доверять.

## Решение

Выбран вариант **A** (решение Dmitry). Для долгих процессов (ковка, госзаявление) он естественен и не требует
переносить данные. B — это остановка, ровно то, чего Strangler Fig избегает. C сильнее всего, но сложнее всего и
почти совпадает с темой 15 (CDC).

Как устроено (решения при проверке спеки «строителем»):
- **Переключатель — флаг в базе монолита** (`migration.forge_cutover`), меняется админ-эндпоинтом без рестарта. Не
  переменная окружения: при рестарте пода незавершённые публикации доставляются заново, и решение «куда» не должно
  зависеть от момента доставки.
- **Адресат выбирается при публикации**, в транзакции заказа, и записан в тип события: `WorkOrderRequested`
  (локальный Forge) или `RemoteWorkOrderRequested` (`@Externalized` в `forge.requests`).
- **Маршруты статические с первого дня**: `WO-…` → монолит, остальной API кузнеца → сервис, который служит
  фасадом и подмешивает открытые заказы монолита. Переключение — только флаг, маршрут не может разойтись с ним.
- **Склад материалов делится**: у каждой стороны своя доля, без синхронизации («склад делится при переезде
  цеха»).
- **Шаги:** `before → cutover → drain → decommission`; `rollback` — флаг обратно, а уже созданные `FW-` доживают в
  сервисе, симметрично `drain`.

### Последствия

- Хорошо: нет синхронизации данных, нет окна остановки, откат — тот же флаг.
- Хорошо: «склад делится» и «старые доживают» легко объяснить бизнесу.
- Плохо: две системы работают одновременно до конца `drain`, и это время задают самые долгие заказы.
- Плохо: список для кузнеца собирается из двух источников. Если монолит молчит, список неполный (`X-Partial`).
- Плохо: нужна вторая доля склада; если её не хватает, сервис заказывает у поставщика.

### Подтверждение

`CutoverIT` (адресат в типе события, откат, вывод из эксплуатации отклоняется, пока есть открытые заказы),
`WorkOrderIntakeIT` (повторная доставка), `scripts/e2e.sh` и `scripts/live.sh` со сверкой: у каждого принятого
заказа ровно один завершённый заказ на ковку на одной из сторон.
