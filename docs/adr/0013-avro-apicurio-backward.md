# ADR-0013: События — Avro в Apicurio Registry, правило BACKWARD, схемы регистрирует пайплайн

## Контекст и проблема

В Kafka живут сообщения разных версий: продюсер уже на новой схеме, а в топике лежат старые. JSON без схемы не
говорит, совместимо ли изменение, — это видно только по падению потребителя.

## Движущие факторы

- Совместимость проверяется до того, как схема попадёт к продюсеру.
- Понятный порядок выкатки.
- Сервисы не должны иметь права менять контракт топика.

## Рассмотренные варианты

- **Avro + Apicurio Registry 3**, правило `BACKWARD`, регистрация из CI.
- Avro + Confluent Schema Registry (та же модель, другая лицензия).
- JSON Schema или Protobuf в реестре.
- Авторегистрация схем продюсером.

## Решение

Выбран **Avro + Apicurio Registry 3** (Apache 2.0, SerDe `apicurio-registry-avro-serde-kafka`), стратегия
`TopicIdStrategy` (`forge.requests-value`, `forge.events-value`), правило `COMPATIBILITY=BACKWARD`. Схемы регистрирует
пайплайн: в CI — `SchemaCompatibilityIT` против выпущенной 1.0.0, в compose — `schema-init`. У сервисов
`auto-register: false`.

### Последствия

- `BACKWARD` — новая схема читает старые данные: первым обновляется **потребитель**. Новые поля — только с
  default; удаление поля — можно; переименование символа enum — нельзя.
- Отвергнутая реестром схема не доедет до продюсера: он её не найдёт и не отправит сообщение.
- Реестр — новая зависимость на пути каждого сообщения (кэшируется SerDe).
- Мусор в топике — в `<topic>.DLT` с исходными байтами (`ErrorHandlingDeserializer`).
