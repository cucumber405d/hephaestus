# ADR-0002: Автомасштабирование — KEDA, консьюмеры по лагу Kafka, вход по CPU

## Контекст и проблема

В саге два вида нагрузки. HTTP-вход (Ordering принимает заказы) нагружает CPU. Участники (Payment, Inventory,
Delivery) и сам Ordering как слушатель ответов работают от Kafka: их нагрузка — это **очередь** (лаг консьюмер-группы),
а CPU может быть низким, пока сообщения копятся. Стандартный HPA по CPU масштабирует консьюмеров поздно или не
масштабирует вовсе.

## Движущие факторы

- Решение Dmitry: KEDA через Kafka.
- Масштаб консьюмеров ограничен числом партиций: сверх него лишние консьюмеры простаивают.
- В kind нет metrics-server (HPA по CPU без него не работает).
- Одна модель управления масштабом для всех сервисов проще, чем смесь HPA и KEDA.

## Рассмотренные варианты

- A. Только HPA по CPU (metrics-server)
- B. HPA по пользовательским метрикам (Prometheus Adapter → `kafka_consumergroup_lag`)
- C. **KEDA**: Kafka-скейлер по лагу для консьюмеров + CPU-триггер для входа; KEDA сам создаёт HPA

## Решение

Выбран **C**.

- KEDA ставится в платформу (Helm-чарт `kedacore/keda` через Argo CD, namespace `keda`), вместе с
  **metrics-server** (для CPU-триггера; в kind — с `--kubelet-insecure-tls`). Версия KEDA выбирается под версию
  Kubernetes узлов kind (2.21 поддерживает 1.34–1.36, 2.20 — 1.33–1.35).
- **Payment, Inventory, Delivery**: `ScaledObject` с триггером `kafka` на свою консьюмер-группу и топики,
  `lagThreshold` — стартово 20 сообщений на реплику, `activationLagThreshold` 0, `minReplicaCount` 1 (не ноль:
  ноль даёт холодный старт посреди саги и проблему с автообнаружением топиков), `maxReplicaCount` = число партиций.
- **Ordering**: два триггера — `cpu` (утилизация 60 %) для приёма заказов и `kafka` на группу `ordering`
  (ответы и события участников); KEDA берёт максимум.
- **Партиции**: в 12 топики саги — 6 партиций (было 3), объявлены как Strimzi `KafkaTopic`; `maxReplicaCount` 6.
  Ключ — id заказа, поэтому порядок сообщений одного заказа сохраняется при любом числе партиций.
- `allowIdleConsumers` — false (по умолчанию): реплик не больше партиций.
- Поведение HPA: масштаб вверх быстро (без стабилизации), вниз — окно стабилизации 120 s, чтобы не дёргать
  ребалансировки (ADR-0003).

### Последствия

- Хорошо: консьюмеры реагируют на очередь, а не на CPU; вход — на CPU; всё — одним видом объекта.
- Хорошо: потолок масштаба консьюмеров виден и объясним (партиции).
- Плохо: KEDA — ещё один оператор в и так тесном кластере; лаг читается KEDA напрямую из Kafka (ещё одно
  подключение к брокеру).
- Плохо: 6 партиций на одном брокере kind — для учебы; в реальности число партиций — решение о ёмкости на годы.

### Подтверждение

`peak.sh` во время пика фиксирует число реплик каждого сервиса (`kubectl get hpa,scaledobject`) и лаг групп;
ожидание: консьюмеры выросли выше 1 и не выше 6, после пика вернулись к 1.

## Плюсы и минусы вариантов

### A. HPA по CPU

- Хорошо: стандарт Kubernetes, один metrics-server.
- Плохо: консьюмеры с низким CPU и растущей очередью не масштабируются.

### B. HPA + Prometheus Adapter

- Хорошо: любая метрика, без нового оператора.
- Плохо: адаптер — сложная конфигурация правил; экспортёр лага Kafka ещё нужно поставить; масштаб в ноль невозможен.
