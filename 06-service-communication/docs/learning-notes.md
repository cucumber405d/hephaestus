# Learning notes — 06-service-communication

## Синхронный вызов: цена

Ordering может принять заказ, только если Inventory ответил. Доступность Ordering ≤ доступности Inventory
(и всех, кого он зовёт), а задержка — сумма задержек. Плюс — простота и мгновенный ответ клиенту «есть/нет».
Асинхронная альтернатива (событие `OrderPlaced`, резерв позже) — 09–10.

## HTTP Service Client

- Интерфейс с `@HttpExchange`/`@GetExchange`/`@PostExchange` → Spring делает прокси поверх `RestClient`
  (`HttpServiceProxyFactory` + `RestClientAdapter`). Это замена OpenFeign: Feign объявлен feature-complete,
  а клиент — часть самого Spring Framework.
- Spring Framework 7: `version` на аннотации + `ApiVersionInserter` у `RestClient` → заголовок `API-Version`
  ставится сам. `@ImportHttpServices` регистрирует прокси группами без кода; здесь фабрика написана явно, чтобы
  видеть таймауты и базовый URL.
- `RestClient.Builder` берётся из Spring Boot (а не `RestClient.builder()`): у него конвертеры Jackson и, позже,
  наблюдаемость (трассировка в 11).
- DTO у каждого сервиса свои (`InventoryHttpApi.ReservationRequest`): общий модуль DTO — скрытая связность
  деплоя. Совместимость форматов проверяют контрактные тесты (14).

## Таймауты

По умолчанию у HTTP-клиентов JDK **нет read timeout**: зависший сосед держит наш поток вечно, потоки кончаются —
каскадный отказ. Здесь connect 1 s (соседа нет — узнаём быстро), read 2 s (бюджет на ответ). Правило: таймаут
вызывающего больше таймаута вызываемого, сумма по цепочке меньше таймаута клиента/Gateway. e2e проверяет: при
остановленном Inventory Ordering отвечает 503 быстрее 5 s.

## Перевод ошибок соседа

Чужие коды наружу не пробрасываются: `409` Inventory → наш `409 insufficient-stock` (SKU из Problem Details
соседа), `404/422` → `422 unknown-item`, `5xx`/нет соединения/таймаут → `503 inventory-unavailable` +
`Retry-After: 5`. Почему 503, а не 502/504: 502/504 говорят прокси; сервис, который сам не может выполнить
запрос из-за зависимости, отвечает 503 и подсказывает, когда повторить. Прочие 4xx от соседа — наша ошибка
в запросе → 500 и лог.

## Почему без ретраев

Повтор после таймаута опасен, если операция не идемпотентна: первый запрос мог дойти. Резерв здесь
идемпотентен по `orderId`: повтор с теми же строками → `200` и тот же резерв, и параллельный тоже (проверено
тестом — оба ждут на одних строках склада). Ограничения: повтор с **другим** набором SKU не делит блокировок,
и два таких параллельных запроса упрутся в уникальный индекс → `500`; повтор с другими строками молча вернёт
первый резерв (правильнее — `409`, если тело отличается, как `Idempotency-Key` в 02). Политика ретраев
(сколько, с каким backoff, когда открывать circuit breaker) — тема 08.

## Удалённый вызов и транзакция БД

`OrderService.place` не `@Transactional`: держать транзакцию (и соединение из пула) открытой во время HTTP-вызова —
пул кончится раньше потоков. Цена: резерв сделан, а сохранение заказа упало → «осиротевший» резерв. Это dual write;
надёжное решение — outbox и сага с компенсацией (10).

## Резерв и блокировки

- Строки склада блокируются `SELECT … FOR UPDATE` **в порядке SKU**: два заказа на {A, B} и {B, A} ждут друг
  друга, а не ловят дедлок.
- Проверка «этот заказ уже резервировал?» — **после** блокировки: параллельный повтор того же `orderId` ждёт на
  тех же строках и находит резерв первого, а не резервирует второй раз. Уникальный индекс `order_id` — страховка.
- Оптимистическая блокировка (`@Version`) здесь хуже: конфликт на горячем товаре → ретраи.

## Версионирование API

- Spring Framework 7 даёт механизм (`@GetMapping(version = "2")`, `ApiVersionStrategy`), Spring Boot 4 — свойства
  `spring.mvc.apiversion.*` (заголовок, поддерживаемые, по умолчанию). Неподдерживаемая версия → 400. Варианты: заголовок (здесь), путь `/v2/...`,
  media type `application/vnd...+json;v=2`, query-параметр.
- Устаревание: `StandardApiVersionDeprecationHandler` добавляет к ответам v1 `Deprecation` (RFC 9745), `Sunset`
  (RFC 8594) и `Link rel="deprecation"` — клиент узнаёт из каждого ответа, до какого числа v1 жив. Устаревание —
  **по версии, а не по эндпоинту**: неверсионированный `/api/reservations` с `API-Version: 1` тоже получил бы эти
  заголовки, а после удаления v1 — `400`. Поэтому Ordering шлёт резерв уже с версией 2.
- Совместимые изменения (новое поле) версии не требуют; несовместимые (удалить/переименовать поле, сменить
  смысл) — новая версия и период параллельной поддержки.

## API Gateway vs Gateway API

- **Envoy / Gateway API (05)** — инфраструктура кластера: хосты, TLS, балансировка, один вход для всех.
- **Spring Cloud Gateway** — прикладной вход одного продукта: какие пути публичны, агрегирование, позже —
  проверка токенов и BFF (07), rate limiting с Redis (08). Маршруты здесь — только конфигурация.
- Server **Web MVC** вариант работает на servlet/virtual threads — без WebFlux (правило проекта).
- `X-Forwarded-*`: Gateway добавляет их только для доверенных адресов (`trusted-proxies`), сервисы строят
  `Location` из них (`server.forward-headers-strategy: framework`). Доверять `X-Forwarded-*` от кого угодно
  нельзя — клиент подделает хост. Сами сервисы (`framework`) доверяют любому отправителю и полагаются на то, что
  снаружи до них не добраться — только через Gateway (сеть Compose, ClusterIP; в 07 — ещё и NetworkPolicy).

## Kubernetes DNS

Service `inventory` в namespace `hephaestus-06` доступен как `http://inventory` (тот же namespace),
`inventory.hephaestus-06`, `inventory.hephaestus-06.svc.cluster.local`. kube-proxy балансирует по готовым
подам (readiness). Отдельный service discovery (Eureka) в Kubernetes не нужен.

## Вопросы для собеседования

1. **Feign vs HTTP Service Client vs RestClient?** Декларативный интерфейс на RestClient — встроен в Spring 7; Feign — отдельная библиотека, feature-complete.
2. **Какие таймауты ставить и почему по умолчанию — плохо?** Connect и read, по бюджету цепочки; без read timeout потоки висят вечно.
3. **Что отвечать, когда сосед недоступен?** 503 + Retry-After; не пробрасывать чужие коды и тексты.
4. **Когда можно ретраить?** Только идемпотентные операции (или с ключом идемпотентности), с backoff и лимитом.
5. **Почему не держать транзакцию во время HTTP-вызова?** Пул соединений, длинные блокировки; dual write → outbox/saga.
6. **Как избежать дедлоков при блокировке нескольких строк?** Один порядок захвата (сортировка ключей).
7. **Как версионировать REST API?** Заголовок/путь/media type; совместимые изменения без версии; Deprecation/Sunset.
8. **API Gateway vs Ingress?** Прикладная логика входа vs маршрутизация трафика кластера; часто оба.
9. **Зачем X-Forwarded-* и чем опасны?** Публичные URL за прокси; доверять только своим прокси.
10. **Service discovery в Kubernetes?** DNS Service + kube-proxy; Eureka не нужна.
