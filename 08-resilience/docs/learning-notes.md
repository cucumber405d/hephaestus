# Learning notes — 08-resilience

## Сравнение трёх механизмов

| | Resilience4j напрямую | Spring Cloud Circuit Breaker | Spring Framework 7 |
|---|---|---|---|
| Зависимость | модули `resilience4j-*` | `spring-cloud-starter-circuitbreaker-resilience4j` | никакой (spring-core) |
| Стиль | код: декораторы над `Supplier` | `factory.create(id).run(call, fallback)` | аннотации на бине (прокси) |
| Circuit breaker | да | да (Resilience4j под капотом) | **нет** |
| Retry | да, гибкий (`IntervalFunction`, предикаты) | **нет в абстракции** | `@Retryable` (includes, backoff, jitter) |
| Bulkhead | да, отказ без ожидания | опционально (R4J bulkhead provider), здесь выключен | `@ConcurrencyLimit` — **ждёт**, а не отказывает |
| Rate limiter | да | нет | нет |
| Time limiter | да (отдельный модуль) | да (по умолчанию в R4J-реализации) | нет (только таймауты клиента) |
| Метрики | `resilience4j-micrometer` | автоматически через R4J | нет своих |
| Сменить реализацию | переписать код | поменять стартер (Spring Retry, Sentinel) | — |
| Конфигурация | в коде (стартер для Boot 4 пока нет) | `Customizer` + свойства | атрибуты аннотаций / плейсхолдеры |

Вывод: **Spring 7** — достаточно для «повторить пару раз и не перегрузить» (идемпотентные вызовы к тому, что
обычно работает); **Resilience4j** — когда нужен circuit breaker, rate limiter и тонкая настройка;
**Spring Cloud CB** — когда важна независимость от реализации или так устроено в организации, но retry
придётся добавлять отдельно.

## Что показывает e2e

При «поставщик лежит» 12 запросов на механизм: у Spring 7 до поставщика доходят **все 36 вызовов** (3 попытки ×
12) — это и есть **retry storm**: упавшего соседа добивают втрое большей нагрузкой. Breaker'ы после окна из 10
вызовов перестают звонить и отвечают из кэша за миллисекунды.

## Таймауты — первая защита

Без read timeout поток ждёт вечно, и никакой breaker не спасёт (у него не будет «отказа», будет зависание).
Здесь connect 500 ms / read 1 s у HTTP-клиента — общие для всех механизмов. Time limiter Spring Cloud (3 s) —
страховка сверху, а не основной таймаут. Бюджет запроса ≈ попытки × таймаут + паузы: 3 × 1 s + 0,2 + 0,4 ≈ 3,6 s.

## Retry: когда помогает и когда вредит

- Только **идемпотентные** операции (здесь — чтение) и только **временные** отказы (таймаут, 5xx, обрыв). 404 —
  ответ, не отказ; другие 4xx — наша ошибка, повтор не поможет.
- **Backoff + jitter**: без jitter все клиенты повторяют в одни и те же моменты (thundering herd).
- Retry над retry (клиент, gateway, сервис) — умножение нагрузки; ретраить на одном уровне.
- Retry снаружи breaker'а: открытый breaker отвечает сразу, и retry его не повторяет.

## Circuit breaker

Окно по количеству (10) или по времени; `minimumNumberOfCalls` — без него Resilience4j ждёт 100 вызовов. Медленные
вызовы тоже отказ (`slowCallDurationThreshold`). Half-open — пробные вызовы, не «всё сразу». Breaker защищает **и
соседа** (даёт подняться), **и себя** (не тратить потоки и время на заведомо неудачные вызовы).

## Bulkhead и concurrency limit

Изоляция ресурсов: медленный сосед не должен занять все потоки. Resilience4j отказывает сразу (быстрый fallback),
Spring 7 `@ConcurrencyLimit` ставит в очередь (клиент ждёт дольше, но не теряет ответ). С виртуальными потоками
пул потоков не кончается — тем важнее ограничить нагрузку на соседа, а не на себя.

## Fallback и кэш

Кэш как запасной ответ — **устаревшие данные**: ответ честно помечен `source: cache` и `fetchedAt`. Что можно
отдавать устаревшим (цена в каталоге), а что нельзя (остаток при резерве) — бизнес-решение. Сломанный Redis не
должен ломать живые ответы — ошибки кэша глотаются и логируются.

## Toxiproxy и chaos

Toxiproxy — TCP-прокси с «токсинами»: latency, bandwidth, timeout, reset_peer, slicer. Удобен в Testcontainers и
Compose. HTTP-ошибки (5xx) он не делает — для них управляемые сбои в самом Supplier. В кластере то же делают
Chaos Mesh / LitmusChaos; устойчивость в mesh (Istio: retries, outlier detection) — тема 19.

7. **Hystrix → Resilience4j → встроенное в Spring 7: что изменилось?**
