---
name: 12 reconcile can no longer report OK on an empty or unreadable dump
description: awk NR == FNR swallowed every id when a dump was empty (database down, empty table) and reconcile said OK; FILENAME-based joins, totals check, open count, CR stripped, read failures retried
---

**RU.** Ревью нашло критическую ошибку в сверке. В `awk`-объединениях первый файл (дамп из базы) отличали от второго
условием `NR == FNR`. Если дамп пуст (база перезапускается, таблица пуста), это условие верно и для второго файла:
все id заказов уходили в таблицу поиска, ни один не считался незакрытым, и сверка печатала `RECONCILE OK` — ровно
в том случае, ради которого она существует. Исправлено:
- файлы различаются по `FILENAME`;
- добавлен итоговый баланс `confirmed + rejected = accepted`;
- новое поле `open` считает каждый незакрытый заказ в любом статусе, а не только `PENDING` и `MISSING`;
- `\r` вырезается из всех дампов, а не только из CSV;
- неудачное чтение резервов повторяется до `EFFECTS_WAIT_S`, а не сразу считается провалом.

Самотест: 6 новых случаев, три из них до правки давали `exit 0`.

**EN.** awk joins used NR == FNR, so an empty first file (database down, empty table) swallowed every order id and
reconcile reported OK. Now FILENAME-based joins, a totals check (confirmed + rejected = accepted), an `open` count
covering any unsettled status, CR stripped from every dump, reservation read failures retried. Six new fixture
cases; three of them exited 0 before the fix.
