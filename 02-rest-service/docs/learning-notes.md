# Learning notes — 02-rest-service

## Схема и миграции

**Решения.**
- Схема — только Flyway, Hibernate `ddl-auto: validate`: сущности проверяются против реальной схемы при старте,
  а не генерируют её. Миграции версионируются в Git и одинаково применяются в тестах, локально и в K8s
  (12-factor: XII admin processes).
- Инварианты дублируются в БД (`check`, `unique`, `foreign key`): приложение проверяет для понятной ошибки,
  БД — как последний рубеж против гонок.
- Уникальность без учёта регистра — функциональный индекс `lower(name)`, а не `unique` на колонке.
- Тесты — на настоящем PostgreSQL 17 (Testcontainers + `@ServiceConnection`), а не на H2: H2 не знает
  `jsonb`, ведёт себя иначе в блокировках и диалекте.

**Подводные камни.**
- `numeric(12,2)` + `BigDecimal`: Java-сторона должна сама отклонять 3 знака после запятой — иначе БД молча
  округлит.
- `timestamptz` хранит момент времени (UTC); `timestamp` без зоны — источник багов при смене часового пояса.
- Изменение уже применённой миграции ломает checksum Flyway — только новые миграции.
- `validate` ловит расхождения типов при старте: `char(3)` в PostgreSQL — это `bpchar`, а Hibernate по умолчанию
  ждёт для `String` `varchar`; `columnDefinition` при валидации не помогает — нужен `@JdbcTypeCode(SqlTypes.CHAR)`.
  С `ddl-auto: update` такое расхождение прошло бы незамеченным.

**Вопросы для собеседования.**
1. *Почему не `ddl-auto: update`?* — Неконтролируемые изменения схемы, нет отката и ревью; в production
   схема — артефакт, который версионируется.
2. *Почему Testcontainers, а не H2?* — Тестируем ту же БД, что в production: диалект, типы, ограничения,
   поведение транзакций.

## Contract-first

**Как устроено.** `catalog-api.yaml` (OpenAPI 3.1) пишется руками и лежит в `src/main/resources/static`.
`openapi-generator-maven-plugin` (`interfaceOnly`) генерирует `CategoriesApi`/`ItemsApi` и DTO в
`target/generated-sources`; контроллеры их реализуют. Нарушил контракт — код не компилируется. Ответы
(коды, заголовки, тела ошибок) дополнительно проверяет контрактный тест (задача 8): генератор видит только сигнатуры.

**Решения.**
- `If-Match` в контракте **необязателен**: при `required: true` сгенерированный код сам ответит `400`
  до нашего `428 Precondition Required`. Обязательность проверяет контроллер, контракт её документирует.
- Тело PATCH — свободный объект (`Map<String, Object>`): сгенерированный класс не отличил бы «ключа нет»
  от `null`, а в JSON Merge Patch это разные операции.
- Деньги в JSON — строка (`"12.50"`), не число: без потери точности на клиентах с `double`.
- `API-Version` не объявлен параметром каждой операции (иначе он попал бы в каждую сигнатуру),
  а описан в `info` и обрабатывается механизмом версионирования Spring.

**Подводные камни.** Поддержка OpenAPI 3.1 в openapi-generator всё ещё помечена как beta (предупреждение
при сборке); сложные конструкции 3.1 (`type: [string, "null"]`, `$defs`) лучше проверять по сгенерированному коду.

**Вопросы для собеседования.**
1. *Contract-first или code-first?* — Contract-first: API согласуется до реализации, клиенты генерируются
   параллельно, контракт — артефакт ревью. Code-first быстрее на старте, но контракт становится побочным
   продуктом аннотаций и легко ломается незаметно.
2. *Как поймать breaking change в API?* — Контракт в Git + diff-инструмент (openapi-diff) в CI; для
   code-first — сравнение сгенерированного документа с предыдущим.

## Домен без фреймворков

**Решения.**
- Домен — records на чистой JDK (правило ArchUnit `domainDependsOnlyOnJdk`): `Item`, `Category`, `Money`,
  идентификаторы, критерии поиска, исключения. Инварианты проверяются в compact constructor — объект в
  невалидном состоянии создать нельзя.
- `Money` **отклоняет** 3 знака после запятой, а не округляет: молча изменить цену хуже, чем отказать.
  Scale нормализуется до 2, иначе `equals` у `BigDecimal` различает `2` и `2.00`.
- Агрегаты ссылаются друг на друга только по id (`Item.categoryId`), а не объектом — граница агрегата и
  транзакции, никаких ленивых связей в домене.

**UUIDv7 vs sequence vs UUIDv4.**
| | `bigserial` | UUIDv4 | UUIDv7 |
|---|---|---|---|
| Генерация | БД (нужен round-trip) | приложение | приложение |
| Порядок | монотонный | случайный | по времени |
| Индекс B-tree | дописывается справа | вставки по всему дереву, page splits | дописывается справа |
| Угадываемость / утечка объёма | да | нет | время создания видно |
`Ids.uuidV7()` — 48 бит миллисекунд + версия 7 + вариант RFC 9562 + `SecureRandom`, ~10 строк без зависимостей.

**Подводные камни.** `UUID.compareTo` сравнивает **знаковые** `long`. У UUIDv7 старший бит — старший бит
48-битной метки времени в миллисекундах, он станет `1` только около 6429 года; на практике порядок верен, но на
это полагаться не стоит: для сортировки сравнивать беззнаково или строковое представление.

**Вопросы для собеседования.**
1. *Почему JPA-сущности — не домен?* — Домен не должен знать о Hibernate (proxy, lazy, no-arg constructor,
   изменяемость); persistence — деталь адаптера, её можно заменить без переписывания бизнес-правил.
2. *Где валидировать — в DTO, в домене или в БД?* — Везде, но разное: DTO — формат запроса (Bean Validation
   из контракта), домен — инварианты, БД — последний рубеж против гонок.

## Problem Details и ошибки

**Как устроено.** Любая ошибка — RFC 9457 (`application/problem+json`) со стабильным `type`
(`https://hephaestus.ibikus.de/problems/<slug>`), `title`, `status`, `detail`, `instance`; ошибки валидации — ещё
`errors: [{field, message}]`. `ProblemDetailsAdvice` наследует `ResponseEntityExceptionHandler`: доменные исключения
маппятся явно, собственные исключения Spring MVC (415, 405, несоответствие типа) получают `type` по статусу вместо
`about:blank`.

**Проверка в сервисе + ограничение в БД.** `CategoryService` проверяет уникальность имени и отсутствие изделий —
для понятной ошибки. Но между проверкой и записью может вклиниться параллельный запрос: поэтому уникальный индекс
и FK в БД, а `JpaCategoryRepository` делает `saveAndFlush`/`flush` и переводит `DataIntegrityViolationException`
в доменные `DuplicateCategoryNameException`/`CategoryInUseException`. Веб-слой знает только домен.

**Подводные камни.**
- Без `flush` нарушение ограничения проявится при коммите — уже за пределами адаптера, и перевести его в
  доменное исключение будет некому.
- `type` — идентификатор, а не обязательно рабочая страница; менять его нельзя — клиенты на него завязываются.
- Не отдавать наружу stack trace и SQL в `detail`.

**Вопросы.**
1. *Зачем Problem Details, если есть свой формат ошибок?* — Стандарт: клиенты, шлюзы и библиотеки понимают
   его без договорённостей; машинно-читаемый `type` отделён от человекочитаемых `title`/`detail`.
2. *Почему проверки и в коде, и в БД?* — Код даёт понятную ошибку, БД гарантирует инвариант при гонке.

## Идемпотентность и Idempotency-Key

**Проблема.** `POST` не идемпотентен: клиент не получил ответ (таймаут, обрыв) и повторил — создалось два изделия.
`PUT`/`DELETE` идемпотентны по определению (повтор даёт то же состояние), `POST` — нет.

**Решение** (`ItemService.create(data, key)` + таблица `idempotency_key`).
1. Клиент шлёт уникальный `Idempotency-Key` (обычно UUID) на каждую *логическую* операцию; повторы — с тем же ключом.
2. Сервис в **одной транзакции** ищет ключ; если он есть — сравнивает SHA-256 запроса: совпал — возвращает
   созданное тогда изделие (`Idempotent-Replayed: true`), не совпал — `409 idempotency-conflict`.
3. Ключа нет — проверяет категорию, **вставляет ключ** (`key`, хэш, `item_id`), затем изделие, и коммитит оба.
4. Ошибка (`422`, `400`, сбой) откатывает транзакцию вместе с ключом — повтор снова честно выполняется.
5. Ключи живут 24 ч (очистка раз в час, `IdempotencyCleanup`).

**Почему одна транзакция.** Первая версия была сервлет-фильтром: «зарезервировать ключ → выполнить → сохранить
ответ» тремя отдельными транзакциями. Падение между ними оставляло вечный резерв (ключ «в работе» 24 часа), а
сбой при сохранении ответа после коммита изделия давал дубль при повторе. Теперь ключ и изделие коммитятся
вместе или не коммитятся вовсе.

**Почему ключ вставляется первым.** Два одновременных запроса оба не видят ключ (чужая вставка ещё не
закоммичена). Второй `INSERT` того же первичного ключа в PostgreSQL **ждёт** окончания первой транзакции и затем
получает `duplicate key` → `409`; клиент повторит и получит изделие. Тест
`concurrentRequestsWithTheSameKeyCreateExactlyOneItem` шлёт 4 запроса одновременно — изделие ровно одно.

**Подводные камни.**
- Хэш считается по **доменным** данным (имя, описание, нормализованная сумма, валюта, категория), а не по байтам
  тела: другой порядок полей или `"120"` против `"120.00"` — тот же запрос.
- Повтор возвращает **текущее** состояние изделия, а не байтовую копию первого ответа; если изделие уже удалено —
  `409`. Это осознанная цена за отказ от хранения ответов.
- Без хэша тот же ключ с другим телом тихо вернул бы чужое изделие.
- Время: `timestamptz` хранит микросекунды, `Instant` в JVM — наносекунды; сервис обрезает время до микросекунд,
  иначе ответ POST и последующий GET отличались бы `createdAt`.

**Вопросы для собеседования.**
1. *Какие HTTP-методы идемпотентны?* — `GET`, `HEAD`, `PUT`, `DELETE`, `OPTIONS`; `POST` и `PATCH` — нет
   (PATCH может быть идемпотентным, но не обязан).
2. *Как сделать POST идемпотентным?* — Idempotency-Key + хранение ответа (Stripe, PayPal, IETF draft
   `Idempotency-Key` header), либо клиентский id ресурса и `PUT`.
3. *Что вернуть, если первый запрос ещё выполняется?* — `409 Conflict` (так советует IETF draft
   `Idempotency-Key`); клиент повторит позже и получит результат первого запроса.

## Поиск, пагинация, N+1

**Как устроено.** `GET /api/items?category=&minPrice=&maxPrice=&q=&sort=-price,name&page=&size=` →
`ItemSearchCriteria` (валидация в домене) → JPA `Specification` (Criteria API) + `Pageable`. Сортировка — только по
белому списку (`name`, `price`, `createdAt`) и всегда с добавочной сортировкой по `id`: при равных значениях
порядок между страницами стабилен.

**`LIKE` и пользовательский ввод.** `q=%` без экранирования найдёт всё, `q=_` — любой символ. `escapeLike`
экранирует `\`, `%`, `_`, запрос использует `ESCAPE '\'`. Регистр: `lower(name) like :pattern`, где шаблон
приводится к нижнему регистру ещё в Java (`toLowerCase(Locale.ROOT)`); для кириллицы
нужна UTF-8 локаль БД (в `postgres:17` она по умолчанию).

**N+1.** Изделие хранит `categoryId`, а не `@ManyToOne Category`, поэтому страница не тянет категории по одной.
Это доказано тестом `aPageCostsExactlyTwoStatements` через Hibernate `Statistics`: `select` страницы + `count`.
Если бы связь была `@ManyToOne(fetch = EAGER)` (по умолчанию для `ManyToOne`!), было бы 2 + N запросов.

**Подводные камни.**
- Spring Data не выполняет `count`, если первая страница неполная — тест на «2 запроса» берёт полную страницу.
- Offset-пагинация на больших таблицах медленная (`OFFSET 100000` читает и выбрасывает строки) и «плывёт»,
  если между запросами вставили строку.

**Offset vs keyset (seek).**
| | Offset (`page`, `size`) | Keyset (`after=<последний ключ>`) |
|---|---|---|
| Переход на произвольную страницу | да | нет |
| Цена глубокой страницы | растёт с offset | постоянная (по индексу) |
| Устойчивость к вставкам | дубли/пропуски | стабильна |
| Общее число страниц | `count(*)` | обычно нет |

**Вопросы для собеседования.**
1. *Что такое N+1 и как его найти?* — 1 запрос за списком + N за связями. Находят логом SQL, Hibernate
   `Statistics`, тестом на число запросов; лечат `JOIN FETCH`/`@EntityGraph`/batch fetching или моделью без связи.
2. *Почему `ManyToOne` по умолчанию EAGER — проблема?* — Каждая загрузка тянет связь, в списках — N+1.
3. *Когда keyset лучше offset?* — Бесконечная лента, большие таблицы, экспорт; offset — когда нужны номера страниц.

## Оптимистическая блокировка через HTTP: ETag, If-Match, 412, 428

**Проблема lost update.** Алиса и Боб открыли изделие версии 0. Боб сохранил цену, Алиса — описание;
без защиты изменение Боба молча исчезло.

**Решение в два слоя.**
1. **HTTP:** каждый ответ несёт `ETag: "<version>"`. Изменяющие запросы обязаны прислать `If-Match` с версией,
   на которой клиент основывал изменение. Нет заголовка — `428 Precondition Required` (RFC 6585); версия устарела
   или заголовок непригоден (`*`, `W/"0"`, список) — `412 Precondition Failed`. Сервис сравнивает версию до записи.
   По RFC 9110 `If-Match: *` и список тегов допустимы; здесь это **осознанное отступление**: сервис требует ровно
   одну конкретную версию, чтобы клиент не мог обойти проверку.
2. **БД:** между проверкой и записью может вклиниться чужой коммит. JPA `@Version` превращает запись в
   `UPDATE … WHERE id = ? AND version = ?`; 0 строк → `ObjectOptimisticLockingFailureException` → тоже `412`.
   `OptimisticLockingIT` воспроизводит именно эту гонку двумя транзакциями (`REQUIRES_NEW`).

**JSON Merge Patch (RFC 7386) vs JSON Patch (RFC 6902).**
| | Merge Patch | JSON Patch |
|---|---|---|
| Формат | частичный документ: `{"price":{"amount":"9.99"}}` | список операций: `[{"op":"replace","path":"/price/amount","value":"9.99"}]` |
| Удаление | `null` | `{"op":"remove"}` |
| Записать `null` как значение | нельзя | можно |
| Массивы | заменяются целиком | поэлементно (`/tags/0`) |
| Content-Type | `application/merge-patch+json` | `application/json-patch+json` |
Merge Patch проще и покрывает 90 % случаев; JSON Patch — когда нужны операции над массивами или `test`.

**Подводные камни.**
- PATCH с `application/json` должен получать `415`, иначе клиенты будут слать что угодно.
- Сгенерированный DTO не отличает «ключа нет» от `null` — поэтому тело PATCH разбирается из `Map`.
- `null` в ответе vs отсутствие поля: контракт говорит «string», не «nullable» — поэтому `non_null`.
- Не менять `@Version` руками: спецификация JPA говорит, что приложению *не следует* этого делать, — иначе
  проверка перестанет защищать.

**Вопросы для собеседования.**
1. *Оптимистическая vs пессимистическая блокировка?* — Оптимистическая: проверка версии при записи, без
   удержания блокировок, для редких конфликтов и долгих «раздумий» пользователя. Пессимистическая
   (`SELECT … FOR UPDATE`): держит строку, для частых конфликтов и коротких транзакций.
2. *Почему 412, а не 409?* — 412 — именно «не выполнено условие запроса (`If-Match`)»; 409 — конфликт
   с состоянием ресурса без условных заголовков.
3. *Что даёт strong vs weak ETag?* — Strong — побайтовая идентичность, годится для `If-Match`; weak (`W/`) —
   смысловая эквивалентность, только для кэширования.

## Версионирование API и публикация контракта

**Версия API.** Spring Framework 7 умеет версионирование из коробки (`spring.mvc.apiversion.*`): здесь — заголовок
`API-Version`, поддерживается `1`, она же по умолчанию; неподдерживаемая версия — `400` с типом
`unsupported-api-version`. Альтернативы: путь (`/v1/...` — нагляден, но версия «прилипает» к URI ресурса),
media type (`application/vnd.hephaestus.v1+json` — строго по REST, но неудобно для клиентов), query-параметр.

**Контракт наружу.** Swagger UI показывает **рукописный** `catalog-api.yaml`; генерация документации из кода
(`/v3/api-docs`) выключена — иначе было бы два «источника правды».

**Контрактный тест.** `CatalogScenarioIT` проходит путь клиента (категория → изделие → поиск → PATCH → устаревший
PUT → DELETE) и каждый запрос/ответ проверяет `openapi-request-validator` против YAML. Проверка мутацией:
контроллер, отвечающий `200` вместо `201`, валидатор ловит сам — «Response status 200 not defined».

## Когда гексагональная архитектура — оверинжиниринг

Для CRUD без правил (админка, справочник) порты и два набора моделей удваивают код без выигрыша: хватит
слоёв controller → service → repository и JPA-сущностей как модели. Гексагональность окупается, когда есть
бизнес-правила, несколько входов (REST + события + batch) или выходов, длинный срок жизни и замена технологий.
Здесь она взята как **эталон** для следующих подпроектов (события в 09–10, gRPC в 14).

**Вопросы для собеседования.**
1. *Как версионировать REST API?* — Путь, заголовок, media type, параметр; главное — не ломать совместимость
   внутри версии (только добавлять поля), депрекейтить с датой, держать контракт-тесты.
2. *Чем контрактный тест отличается от интеграционного?* — Проверяет соответствие формата спецификации
   (коды, заголовки, схемы), а не бизнес-результат; ловит «тихие» нарушения контракта.
