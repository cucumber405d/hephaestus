# 12-scaling-operations — выводы

## HPA vs KEDA

| | HPA по CPU | KEDA (Kafka-лаг) |
|---|---|---|
| Сигнал | загрузка CPU пода | очередь: сообщения, которые ещё не обработаны |
| Консьюмер с низким CPU и растущей очередью | не масштабируется | масштабируется |
| Потолок | `maxReplicas` | `maxReplicaCount` и **число партиций** |
| Масштаб в ноль | нет | да (здесь не используем: холодный старт посреди саги) |
| Как устроено | HPA читает metrics-server | KEDA сам создаёт HPA и отдаёт ему внешнюю метрику |

Вход по HTTP (Ordering) — честнее по CPU: очереди перед ним нет, есть запросы.

## Партиции — решение о ёмкости

Число партиций — максимум параллельных консьюмеров группы. Увеличить можно (ключ — id заказа, порядок одного
заказа сохраняется, но распределение ключей по партициям меняется), уменьшить — нет. Поэтому 6 партиций
объявлены до старта сервисов (`KafkaTopic`, волна 0).

## Фантомный лаг на старте (найдено на первом запуске)

Без единого заказа KEDA раздула все сервисы до 6 реплик: у новых групп нет закоммиченных смещений, и Kafka-скейлер
по умолчанию (`scaleToZeroOnInvalidOffset: false`) считает каждую такую партицию «нужен консьюмер» — лаг =
`lagThreshold`. 24 партиции группы `payment` × 20 = 480 → 24 реплики → упор в 6. `kafka-consumer-groups.sh
--describe` показывал LAG «-» и LOG-END-OFFSET 0 — реального лага не было. Лечится `scaleToZeroOnInvalidOffset:
"true"` при `minReplicaCount ≥ 1`. Урок: метрика масштабирования — не то же самое, что реальность; сверять с
источником.

## Ребалансировка

- Eager (классика): вход/выход любого пода останавливает всю группу.
- Cooperative sticky: инкрементально, но логика на клиенте.
- **KIP-848** (`group.protocol=consumer`, Kafka 4): брокер переназначает только затронутые партиции.
- Статическое членство (`group.instance.id`) — хорошо для перезапусков того же пода, плохо для масштаба вниз:
  партиции ушедшего пода ждут `session.timeout.ms`.

## Почему «ни один заказ не потерян» — это сверка, а не метрика

HTTP-метрики видят только ответ. Сага асинхронна: заказ, принятый `202`, может застрять или потеряться позже.
Поэтому критерий формулируется как деловой инвариант и проверяется после прогона по журналу Gatling и базам
участников (ADR-0001). Отказ по таймауту шага считается провалом: иначе перегрузка маскируется под бизнес-отказ.

## Что осталось за рамками

- **Kafka в одном экземпляре** на эфемерном хранилище: drain её узла потерял бы сообщения. В реальности —
  3+ брокера, `min.insync.replicas` 2, rack awareness, PDB для брокеров (Strimzi делает их сам).
- **Chaos Mesh / Litmus** — помехи как ресурсы кластера, по расписанию.
- **Argo Rollouts / canary** — 20.
- **Распределённый Gatling** — генератор на том же ноутбуке ограничивает пик.
- **Cluster Autoscaler** — узлы не добавляются: поды в `Pending` — это предел kind.
