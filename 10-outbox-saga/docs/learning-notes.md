# Learning notes — 10-outbox-saga

## Transactional outbox

Проблема (09): «сохранить в БД» и «отправить в Kafka» — две системы, общей транзакции нет. Outbox: сообщение
пишется **в ту же БД, в той же транзакции**, а отправляется отдельно после коммита. Гарантия — **at-least-once**
(отправка может повториться), поэтому получатели идемпотентны. Здесь outbox — реестр публикаций Spring Modulith
(`event_publication`): незавершённые публикации переотправляются по расписанию и при рестарте.
Альтернативы: **CDC** (Debezium читает WAL/таблицу outbox — без опроса, но ещё один компонент), «listen to
yourself» (сначала событие, состояние — по своему же событию).

## Сага

Длинный бизнес-процесс через несколько сервисов без распределённой транзакции (2PC блокирует ресурсы и связывает
сервисы). Каждый шаг — локальная транзакция + сообщение; отказ — **компенсирующие** действия для уже сделанных
шагов, в обратном порядке. Компенсация — не откат, а новое бизнес-действие (refund видно в выписке).

## Хореография против оркестрации

| | Хореография | Оркестрация |
|---|---|---|
| Где процесс | размазан по сервисам | в одном месте (оркестратор) |
| Связность | сервисы знают события друг друга | участники знают только свои команды |
| Изменить порядок шагов | правки в нескольких сервисах | правка в оркестраторе |
| Видимость | нужен трекер событий (здесь — Ordering) | состояние саги в таблице |
| Таймауты | **некому держать** — заказ висит (сценарий 7) | дедлайн шага + компенсации |
| Отмена поздних действий | нет (Delivery не знает про отказ) | `CancelDelivery` |
| Узкое место | нет центра | оркестратор (масштабировать, не терять состояние) |
| Подходит | 2–3 шага, простые реакции | много шагов, ветвления, таймауты, SLA |

## Идемпотентность и «семантические блокировки»

- Повтор сообщения (`messageId`) — пропуск; повтор действия по заказу — тот же результат (один резерв на заказ).
- Компенсация без действия — no-op, но **запоминается**: refund/release/cancel, пришедшие раньше резерва (таймаут
  оркестратора), запрещают поздний резерв. Без этого после таймаута деньги зависли бы.
- Порядок команд одного заказа сохраняется ключом `orderId` (одна партиция): Schedule, затем Cancel.

## Таймауты

Таймаут не отличает «медленно» от «умер» (сценарий 8). Поздний ответ после таймаута игнорируется, а действие,
которое всё же случилось, отменяется компенсацией. Выбор таймаута — компромисс между скоростью ответа клиенту и
ложными отказами.

## Движки процессов

Temporal, Camunda 8 (Zeebe), AWS Step Functions берут на себя состояние, ретраи, таймеры, версионирование
процессов, наблюдаемость. Здесь оркестратор написан руками, чтобы видеть механику; в бою для сложных процессов —
движок.

## Вопросы для собеседования

1. **Почему не 2PC между сервисами?** Блокировки, доступность, координатор — точка отказа; брокеры не участвуют.
2. **Что такое transactional outbox и какие гарантии он даёт?** Атомарность состояния и сообщения; at-least-once.
3. **Outbox против CDC?** Опрос таблицы vs чтение журнала БД.
4. **Хореография или оркестрация — как выбрать?** Число шагов, таймауты, видимость, связность.
5. **Что такое компенсация и почему она не rollback?** Новое бизнес-действие, видимое и необратимое по-своему.
6. **Как сделать компенсацию безопасной при повторе и при гонке с действием?** Идемпотентность, запоминание отмены.
7. **Что делать с ответом, пришедшим после таймаута?** Игнорировать и компенсировать последствия.
8. **Где хранить состояние саги?** В БД оркестратора, в той же транзакции, что и отправка команд (outbox).
9. **Как наблюдать за сагой?** История/журнал, correlation id = orderId, трассировка (тема 11).
10. **Чем помогают Temporal/Camunda?** Долговечное состояние, таймеры, ретраи, версии процессов.
