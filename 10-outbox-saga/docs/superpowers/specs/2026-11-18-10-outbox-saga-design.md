# 10-outbox-saga — design

## Зачем

В 09 осталась дыра **dual write**: заказ сохранён, а событие может не дойти. Здесь её закрывает **outbox**
(Spring Modulith Events), и на нём строится распределённый бизнес-процесс — **сага** заказа
Ordering → Payment → Inventory → Delivery с **компенсациями** при отказе шага. Обе формы саги — **хореография**
и **оркестрация** — живут рядом: стиль выбирается у заказа, одни и те же сбои прогоняются через оба и сравниваются
(формат 08). Площадка для опытов руками, как в 09: рычаги, Kafka UI, история саги видна в API.

Успех: по `docs/start.md` любой сценарий повторяется руками в обоих стилях; e2e проходит все сценарии;
learning notes содержат таблицу сравнения стилей.

## Цели / не-цели / анти-цели

- Цели: transactional outbox (событие в той же транзакции, доставка после коммита, повтор после сбоя Kafka);
  сага с компенсациями в обратном порядке; хореография и оркестрация на одних участниках; идемпотентные
  участники и компенсации; таймаут шага у оркестратора; история саги.
- Не-цели: безопасность, k8s, Schema Registry, движки процессов (Temporal/Camunda — в learning notes),
  реальные платежи.
- Анти-цели: «распределённая транзакция» как 2PC; компенсация, которая сама может сломать данные при повторе.

## Подход

| Вариант | Решение |
|---|---|
| (а) обе саги рядом, стиль у заказа | ✔ |
| (б) только оркестрация, хореография на бумаге | нет — сравнение руками ценнее |
| Оркестратор: **свой в Ordering** (таблица саги, команды/ответы через Kafka) | ✔ |
| Оркестратор: Temporal / Camunda 8 | тяжело и прячет механику — в learning notes |
| Spring State Machine | почти не развивается — нет |

## Состав (Compose, без k8s)

Сервисы `ordering`, `payment`, `inventory`, `delivery` (Java 25, Boot 4.1.2, Spring Modulith 2.1 events с
JDBC-реестром публикаций + `spring-modulith-events-kafka`), одна PostgreSQL с четырьмя базами (по базе на
сервис — данные не общие), Kafka 4.2.2 (как в 09), Kafka UI 8085. Порты: Ordering 8080, Payment 8081,
Inventory 8082, Delivery 8083. Пакеты `de.ibikus.appa.hephaestus.outboxsaga.<service>`; образы
`hephaestus/outbox-saga-<service>`.

## Бизнес-правила участников (естественные отказы)

- **Payment**: у покупателя кредитный лимит (alice 1000.00, bob 50.00, остальные 500.00 EUR); резерв суммы
  заказа, `refund` возвращает. Не хватает лимита → отказ.
- **Inventory**: склад как в 06 (ANVIL-01 10, HAMMER-01 25, TONGS-01 0); резерв всех строк или ничего,
  `release` возвращает.
- **Delivery**: планирует доставку; отказ по рычагу (`failCustomers`) — «нет курьера в регионе».
- **Ordering**: цены — фиксированный каталог в коде (ANVIL-01 120.00, HAMMER-01 35.00, TONGS-01 18.50).
- У всех: `/admin/faults {failCustomers, transientFailures, delayMs}` (как в 09), `/admin/stats`.

## Сага

Заказ `POST /api/orders {customerId, saga: "choreography"|"orchestration", lines}` → **202** `{id, status:
PENDING}`; `GET /api/orders/{id}` → статус (`PENDING`, `CONFIRMED`, `REJECTED`) + **история** (шаг, событие,
время). Шаги: payment → inventory → delivery. Компенсации при отказе шага N — откат шагов N-1…1 в обратном
порядке (refund, release); заказ `REJECTED` с причиной.

- **Хореография**: события в топиках `<service>.events` (`OrderPlaced`, `PaymentReserved|PaymentDeclined|
  PaymentRefunded`, `StockReserved|StockUnavailable|StockReleased`, `DeliveryScheduled|DeliveryFailed`).
  Каждый реагирует на чужие события; Ordering слушает всё и ведёт статус. Центрального знания о процессе нет.
- **Оркестрация**: Ordering хранит сагу (`saga`: шаг, состояние, дедлайн шага) и шлёт команды в
  `<service>.commands` (`ReservePayment`, `RefundPayment`, `ReserveStock`, `ReleaseStock`, `ScheduleDelivery`),
  участники отвечают в `ordering.replies`. **Таймаут шага 30 s** (`@Scheduled`) → компенсации.
- Участник обрабатывает одно и то же действие из обоих стилей одним кодом; стиль определяет только, откуда
  пришёл вход и куда уходит результат.
- **Идемпотентность**: у каждого сообщения `messageId`; участники хранят обработанные (как в 09); резерв по
  `orderId` один раз; refund/release без резерва — no-op, повторный — no-op.
- **Outbox везде**: любое исходящее событие/команда/ответ публикуется через `ApplicationEventPublisher` в
  транзакции изменения состояния; Spring Modulith пишет его в реестр (`event_publication`) и отправляет в
  Kafka после коммита (`@Externalized`, ключ — `orderId`). Незавершённые публикации переотправляются
  (по расписанию через `IncompleteEventPublications`/`FailedEventPublications` и при рестарте).

## Сценарии (оба стиля; start.md + e2e)

1. Счастливый путь → CONFIRMED, история payment → stock → delivery.
2. Нет лимита (bob, дорогой заказ) → REJECTED на первом шаге, компенсаций нет.
3. Нет товара (TONGS-01) → refund → REJECTED.
4. Delivery отказывает → release + refund → REJECTED.
5. **Outbox**: остановить Kafka, сделать заказ → 202, в `event_publication` незавершённая запись; запустить
   Kafka → сага доходит до конца.
6. Дубль команды/события (рычаг повтора в участнике) → действие выполнено один раз.
7. **Участник лежит**: остановить Delivery. Оркестрация: через 30 s таймаут → компенсации → REJECTED.
   Хореография: заказ висит в PENDING, пока Delivery не вернётся (затем доходит) — главный пункт сравнения.

## Тесты

Unit (правила участников, переходы саги, компенсации, идемпотентность); IT на Testcontainers (Kafka 4.2,
PostgreSQL) по сервису: outbox пишет публикацию в транзакции и доставляет после коммита; оркестратор с
заглушками участников (успех, отказ, таймаут); e2e — сценарии 1–7 в обоих стилях (5 и 7 — с остановкой контейнеров).

## Мои решения (можно оспорить)

- Одна PostgreSQL с базами по сервису (легче, чем 4 контейнера; изоляция данных сохранена).
- Деньги — `BigDecimal` EUR, без валют. Лимиты и склад — сид-данные в миграциях.
- Ответ на заказ — 202 и опрос `GET`, без WebSocket/SSE.
- Ordering не вызывает участников по HTTP вообще — только сообщения.
- Таймаут шага только у оркестратора (у хореографии его некому держать — это и показываем).
