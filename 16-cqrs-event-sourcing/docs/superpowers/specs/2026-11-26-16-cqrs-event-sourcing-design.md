# 16-cqrs-event-sourcing — design

## Зачем

До 16 состояние наряда в Forge — строка в таблице: `status` перезаписывается, история теряется, а события для
других сервисов — побочный продукт (outbox в 10/14/15). Event sourcing (ES) переворачивает это: источник истины —
журнал событий агрегата, состояние восстанавливается из него. CQRS (Command Query Responsibility Segregation)
разделяет запись (команды → события) и чтение (проекции — read models, построенные по журналу). Цель подпроекта —
разобрать механику руками: журнал, конкурентная запись, проекции и их checkpoint, replay, эволюция событий,
«время назад» (time travel). Проект идёт в учебник: каждая деталь должна быть видна в коде, без фреймворка-магии.

Решения Dmitry: продолжение истории 13–15 (Ordering → Forge); event-sourced агрегат — наряд (`WorkOrder`) в Forge,
склад — тоже из событий (проекция «складской журнал»); event store — **свой, на PostgreSQL** (не Axon, не KurrentDB:
они — в ADR как сравнение); общий набросок (ниже) утверждён.

## Цели / не-цели / анти-цели

- **Цели**
  - Event store в Forge на PostgreSQL: append-only журнал, оптимистичная конкуренция по версии потока, чтение
    потока и чтение «всего журнала по глобальной позиции» для проекций.
  - Два event-sourced агрегата в Forge (решение моё, обоснование — в «Как устроено»):
    - `WorkOrder` (поток на наряд): `WorkOrderRequested`, `WorkOrderFailed(reason)`, `MaterialAllocated`,
      `WorkOrderStarted(smith)`, `WorkOrderCompleted`.
    - `Material` (поток на материал): `StockReceived(quantity, source)`, `StockTaken(quantity, workOrderId)`;
      инвариант «остаток ≥ 0» проверяется на версии потока материала.
  - Поведение Forge снаружи — как в 15 (gRPC-цена, приём `WorkOrderRequest`, отказы с причиной, поставщик с
    повторами, `start`/`complete` по REST, `ForgeEvent` обратно в Ordering); меняется внутреннее хранение.
    `start` получает параметр `smith` (кто взял наряд).
  - Конкуренция видна: два кузнеца берут один наряд одновременно — один успешен, второй получает `409`
    (конфликт версии потока).
  - **Журнал = outbox.** `ForgeEvent` в Kafka шлёт publisher, читающий журнал со своего checkpoint (at-least-once;
    Ordering уже идемпотентен). Отдельной outbox-таблицы в Forge нет.
  - **Проекции (read side)**, асинхронные, каждая со своим checkpoint, обновление read model и checkpoint — в одной
    транзакции:
    1. `workshop-board` — наряды по состояниям (заменяет текущий `GET` списка нарядов);
    2. `smith-load` — сколько нарядов в работе и выполнено у каждого кузнеца;
    3. `stock-ledger` — остаток по материалам и история движений.
  - **Time travel:** «остаток материала на момент T» — свёртка событий потока `Material` до `recorded_at ≤ T`
    прямо из журнала (не из проекции); в учебнике — сравнение с проекцией «сейчас».
  - **Replay:** перестроить проекцию с нуля (сброс read model + checkpoint) по запросу администратора; добавить
    проекцию «задним числом» — она догоняет всю историю.
  - **Эволюция событий:** `WorkOrderStarted` v1 (без `smith`) → v2 (с `smith`); upcaster поднимает v1 при чтении
    (v1 со `smith = "unknown"`). В журнале при старте лежат события v1 (фикстура миграции), чтобы upcaster работал
    на настоящих данных. Фикстура — «историческая» (моё): её наряды не связаны с заказами Ordering;
    checkpoint publisher'а миграция ставит **после** фикстуры (в Kafka она не уходит); проекции читают её
    (так «unknown» виден в `smith-load`, фикстурный материал — в `stock-ledger`); сверка учений учитывает только
    заказы, размещённые самим учением.
  - **Учения** (`scripts/drills.sh`, Compose; итог — сверка «каждый принятый заказ на изделие → ровно один наряд,
    состояние Ordering и проекций согласовано»):
    1. Два кузнеца одновременно берут один наряд (много раз): ровно один успех на наряд, остальные — 409.
    2. Удалить read model `workshop-board` и перестроить: результат совпадает с исходным (контрольная сумма).
    3. Включить `smith-load` после N заказов: проекция догоняет всю историю.
    4. `kill -9` Forge во время потока заказов: после рестарта проекции и publisher продолжают с checkpoint;
       ни одного потерянного события, дубли `ForgeEvent` допустимы и безвредны.
    5. Задержка проекции (запись события → строка в read model), p50/p95 под нагрузкой.
- **Не-цели**
  - Snapshot'ы (потоки нарядов короткие) — только объяснение в learning-notes, когда нужны.
  - Event store как отдельная библиотека или отдельный сервис; ES в Ordering.
  - Debezium и Kafka Connect (предмет 15): Ordering отправляет запросы relay'ем Spring Modulith, как в 14
    (решение моё: утяжеляет Compose, CI и платформу без пользы для темы 16).
  - Распределённые саги поверх ES, GDPR/crypto-shredding (только упоминание в learning-notes).
- **Анти-цели**
  - Проекция, которая молча пропускает событие (см. «глобальный порядок») — хуже, чем падение.
  - Состояние нарядов, которое читается мимо журнала (прямые `UPDATE` статуса).
  - Фреймворк, скрывающий механику.

## Как устроено (решения, мои — помечены)

- **Журнал** (схема `forge`, таблица `event`): `global_position bigserial`, `stream_id`, `stream_type`,
  `version int`, `type`, `schema_version int`, `payload jsonb`, `metadata jsonb` (correlation id, causation id),
  `recorded_at timestamptz`, `tx_id xid8 default pg_current_xact_id()`; `unique (stream_id, version)`.
  Добавление: ожидаемая версия потока → вставка версий `expected+1…`; нарушение уникальности = конфликт
  конкуренции (`ConcurrencyConflict`). Удаления и обновления строк журнала запрещены (права БД или триггер — за
  строителем).
- **Глобальный порядок (моё решение, ключевой пункт учебника).** `bigserial` выдаёт номера в момент вставки, а
  коммит может прийти позже: проекция, читающая «позиция > checkpoint», рискует перескочить событие ещё не
  закоммиченной транзакции. Читатель журнала берёт только события с `tx_id < pg_snapshot_xmin(pg_current_snapshot())`
  (старше самой старой незавершённой транзакции) — без глобальной блокировки записи — **в порядке
  `(tx_id, global_position)`**, и checkpoint хранит **оба** значения (моё, после проверки строителем): одного
  `position` мало — транзакция с меньшим `tx_id` может держать позицию между позициями уже закоммиченной
  транзакции с большим `tx_id` (пример: T2 xid 100 пишет 5 и 7, T1 xid 101 пишет 6 и ещё открыта → checkpoint по позиции
  ушёл бы на 7, и 6 потерялась бы). Альтернатива (advisory lock на каждую запись) — в ADR как отвергнутая.
  Обязательны IT: (а) долгая транзакция держит меньшую позицию, более поздняя коммитится раньше; (б) пример выше
  с двумя событиями в одной транзакции — проекция не пропускает ни одного события.
- **Агрегаты** — чистый домен: `decide(command, state) → events`, `evolve(state, event) → state` (функциональный
  стиль, Java 25 records + sealed interfaces). Загрузка = чтение потока + свёртка `evolve` с upcaster'ом.
- **Наряд и склад в одной транзакции (моё решение).** Выделение материала дописывает `StockTaken` в поток
  материала и `MaterialAllocated` в поток наряда одной транзакцией БД (обе проверки версий). Чистый подход —
  process manager между агрегатами; здесь общая БД делает атомарность дешёвой — компромисс описан в ADR.
- **Поставщик** — как в 15: недостающее заказывается, `StockReceived(source=SUPPLIER)` и `StockTaken` пишутся
  вместе; недоступный поставщик — повтор по расписанию (поиск ожидающих нарядов — по проекции `workshop-board`
  или отдельному запросу к журналу — за строителем).
- **Ответы на гонки (моё):** и конфликт версии потока, и доменный отказ («наряд уже взят») дают `409` —
  учение 1 считает «ровно один успех, остальные 409». REST-команды не повторяются автоматически (иначе гонка
  превращается в доменную ошибку и не видна). Приём из Kafka при конфликте версии потока материала (два наряда
  делят материал) повторяет команду ограниченное число раз, дальше — обычная обработка ошибок Kafka (DLT).
- **Идемпотентность приёма:** повторный `WorkOrderRequest` для того же заказа ничего не меняет (id потока выводится
  из `orderId`, повтор упирается в версию 1).
- **Проекции** работают в процессе Forge (поллинг журнала, интервал настраивается), таблицы — в схеме `read`,
  checkpoint'ы — `read.projection_checkpoint(name, tx_id, position)`. **Один писатель на проекцию** (моё):
  обработчик пачки берёт строку checkpoint `SELECT … FOR UPDATE` — две реплики Forge или rebuild во время работы
  поллера не обновят read model дважды. На платформе Forge — 1 реплика, но защита не зависит от этого. Replay — `POST /admin/projections/{name}/rebuild`
  и статус `GET /admin/projections`. Включение проекции — свойство (`projections.<name>.enabled`).
- **Publisher** `ForgeEvent` — особая «проекция» с выходом в Kafka; checkpoint сдвигается после подтверждения
  отправки (at-least-once). Формат `ForgeEvent` — контракт 14 **без изменений** (Avro через Apicurio), и
  последовательность та же, что шлёт 15 (моё): `WorkOrderCompleted` → «готово», `WorkOrderFailed` → «отклонено с
  причиной»; остальные события журнала (включая поток `Material` и `MaterialAllocated`) publisher пропускает.
  `smith` в контракт не попадает.
- **Upcasting** — цепочка upcaster'ов по `(type, schema_version)` при чтении; запись — всегда последняя версия.
- **Ordering** — как в 14 (relay Spring Modulith, `republish-outstanding-events-on-restart`), Flyway с
  `default-schema: public` (урок 15).

## Решения → ADR

- 0017 — свой event store на PostgreSQL (сравнение: Axon Framework + Axon Server, KurrentDB).
- 0018 — глобальный порядок журнала через `xid8`/`pg_snapshot_xmin` (отвергнуто: advisory lock на запись).
- 0019 — журнал как outbox; два потока в одной транзакции вместо process manager.
